# What's new in 1.2.0

1.2.0 introduces `@tvmjs/client` (a local TRON development node), aligns Energy and state
operations with `java-tron` for implemented execution paths by removing Ethereum's EIP-2929
warm/cold storage pricing, establishes standalone TRON execution profiles by removing unsupported
Ethereum legacy mechanisms, preserves 64-bit TRC-10 token ID precision, and delivers an
experimental `java-tron` RPC client PoC.

`@tvmjs/client` is `1.0.0`. `@tvmjs/binarytree`, `@tvmjs/block`, `@tvmjs/blockchain`,
`@tvmjs/common`, `@tvmjs/statemanager`, `@tvmjs/tvm`, `@tvmjs/tx`, `@tvmjs/util` and `@tvmjs/vm` are
`1.2.0`. `@tvmjs/mpt` is `1.0.2`. `@tvmjs/rlp` remains `1.0.0`.

## Upgrading from 1.1.0

### 1. Unsupported Ethereum features removed

Several Ethereum-only features, options, and transaction types that do not exist on TRON have been
completely removed:

- **EIP-7702 authorization processing**: Authority nonce/code updates, authorization refunds, and the
  delegated-sender exception are removed. Retired transaction contexts are rejected before execution.
- **EIP-4788 Beacon root**: Ring-buffer writes and `historicalRootsLength` are removed.
- **Blob transactions (Type `0x03`)**: Blob fees, blob gas calculations, receipt metadata, and
  `allowNoBlobs` are removed. `generateTxReceipt()` now takes four arguments.
- **Contract size flags removed**: `tvmOpts.allowUnlimitedContractSize` and
  `tvmOpts.allowUnlimitedInitCodeSize` are rejected before initialization. TRON deployment limits and
  code-deposit Energy follow `java-tron` rules directly.

### 2. Warm/cold access pricing removed (Energy alignment)

Ethereum's EIP-2929 warm/cold storage and address access pricing has been removed. Account access,
storage operations (`SLOAD`/`SSTORE`), `CALL`/`CALLTOKEN`, `SELFDESTRUCT`, and refund behaviors are
now aligned with `java-tron` Energy rules for implemented execution paths and verified test cases
(noting that dynamic penalties, version-1 contracts, and full on-chain resource models remain outside
the scope of local simulation). Access lists remain diagnostic metadata and do not alter execution
costs.

### 3. Standalone TRON execution profiles

`TronMainnet`, `TronNile`, and `TronShasta` presets are now fully independent TRON execution profiles:

- Ethereum hardfork scheduling, genesis specifications, and block reward mechanisms have been decoupled.
- Conflicting `Common` settings and parameter overrides across `VM` and `TVM` initialization are
  strictly rejected rather than silently discarded.
- Ethereum configurations and legacy combinations like `new Common({ chain: Mainnet, hardfork: 'tron' })`
  are rejected at initialization. Code targeting TRON must use `TronMainnet`, `TronNile`, or `TronShasta` directly.

## Local TRON development node (`@tvmjs/client`)

`@tvmjs/client` provides an in-memory TRON development node with pre-funded accounts, immediate and
interval block mining, and the standard TRON HTTP REST API (`/wallet/*`).

### Installation and CLI

Install the client into your project or run it directly via npx with the scoped package name:

```sh
# Option A: Install locally in your project
npm install --save-dev @tvmjs/client
npx tvmjs

# Option B: Run directly via npx without local install
npx --package=@tvmjs/client tvmjs
```

By default, the client starts an HTTP service at `http://127.0.0.1:9090` and prints 10 pre-funded
development accounts, mnemonics, and private keys.

```sh
# Query the head block
curl http://127.0.0.1:9090/wallet/getnowblock
```

### Programmatic API

Embed a local TRON node directly into testing scripts or development environments:

```ts
import { TronNode, TronProvider } from '@tvmjs/client';

const node = await TronNode.create();
const provider = new TronProvider(node);

// Mine blocks on demand
await node.tre.mine(1);

// Query using standard TRON wallet RPC methods in-process
const block = await provider.request({ method: 'wallet/getnowblock' });
console.log(block.block_header.raw_data.number);
```

## TRC-10 token ID precision

1.1.0 converted token IDs to JavaScript `number` values, limiting safe token IDs to `2^53 - 1`.
1.2.0 preserves full 64-bit token ID precision (`bigint`) across transactions, account balances,
serialization, and state management, preventing collisions and guaranteeing asset isolation through
nested calls, checkpoints, and rollback.

## Experimental java-tron RPC Client PoC

1.2.0 includes an experimental `java-tron` RPC client proof-of-concept that loads remote accounts,
balances, code, and storage from a live TRON node for local read-only TVM execution. It compares the
execution result with `triggerconstantcontract`, reporting snapshot consistency and Energy metering
differences.

## Tested java-tron parity

- Verified 71 measured `java-tron` execution cases through signed local transactions with both
  `SimpleStateManager` and `MerkleStateManager`.
- Cleaned up obsolete Ethereum state/blockchain test runners and fixture submodules, standardizing the
  VM API test suites on pinned TRON Solidity fixtures.
