# What's new in 1.1.0

1.1.0 is about matching `java-tron` rather than approximating it. Address derivation, energy
forwarding, deployment limits and proposal gating now follow the reference client, with improved
error handling and state rollback during execution.

`@tvmjs/common`, `@tvmjs/tvm`, `@tvmjs/util` and `@tvmjs/vm` are `1.1.0`. `@tvmjs/block`,
`@tvmjs/blockchain`, `@tvmjs/binarytree`, `@tvmjs/mpt`, `@tvmjs/statemanager` and `@tvmjs/tx` are
`1.0.1`.

## Upgrading from 1.0.0

Four changes will break existing code. Work through them in order.

### 1. The default chain is now TRON

Without an explicit `Common`, `createVM()` and `createTVM()` use the execution-only `TronMainnet`
preset (chainId `728126428`, hardfork `tron`) instead of Ethereum Mainnet.

```ts
// Ethereum rules
const vm = await createVM({ common: new Common({ chain: Mainnet }) });
```

`new Common({ chain: Mainnet })` is now plain Ethereum Mainnet — it no longer reproduces 1.0.0's
chainId 1 + TRON hardfork combination. The legacy explicit
`new Common({ chain: Mainnet, hardfork: 'tron' })` still works and is normalised to `TronMainnet`.

### 2. `generateAddress2()` is Ethereum again

It returns to EIP-1014's `0xff` preimage. TRON CREATE2 moves to a new helper:

```ts
import { generateTronAddress2 } from '@tvmjs/util';

const address = generateTronAddress2(deployer, salt, initCode);
```

### 3. TRON deployments need a transaction ID

Top-level deployments and internal `CREATE` derive their address from the root transaction ID, so
`rootTransactionId` is required. `runTx()` falls back to the signed transaction hash by default; set
`tronTransactionIdPolicy: 'require-explicit'` for real-chain replay.

::: warning The fallback changes the address
The fallback is a Keccak hash of the serialized TVMJS transaction, not `java-tron`'s SHA-256
transaction ID, so it produces a different contract address. See
[Transaction IDs](/tron/transaction-ids).
:::

### 4. Chain-bound transactions must match the VM

EIP-155 and typed transactions whose chainId differs from the VM are rejected:

```ts
const tx = createLegacyTx(data, { common: vm.common });
```

Unprotected legacy transactions carry no chainId and are still accepted.

## java-tron parity

- Top-level deployments and internal `CREATE` derive addresses from the root transaction ID and the
  21-byte owner address; `CREATE`/`CREATE2` return the 21-byte TRON representation on the stack while
  internal account addresses stay 20 bytes.
- The shared TRON internal nonce advances across nested `CALL`, `CREATE` and `CREATE2`, on
  `CREATE`/`CREATE2` collisions, and on every nested `SELFDESTRUCT`.
- Version-0 execution forwards requested energy up to all available energy across the CALL and CREATE
  families (including `CALLTOKEN`, without the EIP-150 63/64 reserve), matching `java-tron`.
- `SELFDESTRUCT` charges new-account energy when the beneficiary does not exist regardless of the
  transferred value, and does not charge for an existing empty account.
- `CALLTOKEN` and `TOKENBALANCE` validate only the TRC-10 token ID range, so valid but unissued IDs
  continue or return zero.
- Ethereum's EIP-170 runtime-size and EIP-3860 initcode limits no longer apply on TRON chain profiles.

## TRON chain configuration

- New execution-only presets `TronMainnet`, `TronNile` and `TronShasta`, plus a
  `createTronChainIdCommon(network, opts?)` factory.
- `Common.isTron()` reports TRON chain-level behaviour even when a preset selects an earlier hardfork.
- `activatedProposals`, `Common.activatedProposals()` and `Common.isActivatedProposal(id)` gate
  Proposal 95 (`ALLOW_TVM_PRAGUE`) and 96 (`ALLOW_TVM_OSAKA`).

See [Chain Configuration](/guide/chain-configuration).

## Execution safeguards

- Improved rollback handling for unexpected `runCall()` errors, including errors from event hooks.
- Improved block checkpoint handling when finalization fails in `runBlock()`.
- Improved journal bookkeeping and retry handling for transient rollback failures.
- Public `runCall()` and `runCode()` executions are serialised.
- Event listeners keep registration order, `once()` semantics and custom context, including listeners
  that throw.

Rollback behaviour depends on the type of failure; ordinary TVM execution errors retain the existing
top-level nonce semantics. See [Executing Code](/guide/execution#failures-are-atomic) for details.

## New APIs

- Address conversion in `@tvmjs/util`: `toTronHexAddress`, `fromTronHexAddress`,
  `toTronBase58Address`, `fromTronBase58Address`, `isValidTronBase58Address` — cross-validated against
  TronWeb 6.3.0.
- `generateTronCreateAddress(rootTransactionId, nonce)` and `generateTronAddress2()`.
- `TronTransactionIdPolicy` with `fallback-to-tx-hash` and `require-explicit` modes.

## Hardening

- TRON signature precompiles check the signature count before extraction and always read fixed
  65-byte signatures.
- EIP-1186 account proofs are bound to the StateManager state root and storage proofs to the
  authenticated account storage root; proofs for nonexistent accounts are rejected.
- MPT and binary-tree checkpoint reads stay coherent with the optional LRU cache.
- Token fields are rejected on EIP-2930, EIP-1559, EIP-4844 and EIP-7702 transactions.
- Dependency updates for known vulnerabilities (vitest, js-yaml, nanoid).
